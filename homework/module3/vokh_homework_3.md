## Завдання 1. Аналіз HTTP-заголовків (2 бали)

### Команди

```bash
curl -I http://wikipedia.org    # -I = запит HEAD, лише заголовки відповіді
```

### Результат

```text
HTTP/1.1 301 Moved Permanently
content-length: 0
location: https://wikipedia.org/
server: HAProxy
x-cache: cp3070 int
x-cache-status: int-tls
connection: close
```

### Аналіз

| Заголовок / поле | Значення | Пояснення |
| --- | --- | --- |
| **Версія HTTP** | `HTTP/1.1` | Сервер відповів за протоколом HTTP/1.1. |
| **Статус-код** | `301 Moved Permanently` | Клас 3xx — перенаправлення. 301 означає, що ресурс **назавжди** переїхав на іншу адресу. Браузер і пошуковики запам'ятовують нову адресу. |
| **location** | `https://wikipedia.org/` | Куди саме треба йти. Це та сама сторінка, але через **HTTPS**. |
| **content-length** | `0` | Тіла відповіді немає. Для редиректу воно не потрібне. |
| **server** | `HAProxy` | Програма, яка відповіла: балансувальник навантаження HAProxy на вході Wikimedia. |
| **x-cache** | `cp3070 int` | Нестандартний заголовок Wikimedia: ім'я кеш-сервера (`cp3070`), який обробив запит. `int` = відповідь згенерована на самому вузлі (internal), а не взята з кешу. |
| **x-cache-status** | `int-tls` | Внутрішня відповідь, пов'язана з TLS: вузол сам видав редирект на HTTPS. |
| **connection** | `close` | Після відповіді сервер закриває TCP-з'єднання. |

**Чому редирект?** Wikipedia не обслуговує сайт через незахищений HTTP. Будь-який запит на `http://` сервер одразу перенаправляє на `https://`. Так весь трафік іде зашифрованим. Код саме 301 (а не 302), бо це постійне правило, а не тимчасове.

## Завдання 2. POST-запит до власного тестового API (2 бали)

### Команди

Мінімальний тестовий сервер (`test_api.py`):

```python
from http.server import BaseHTTPRequestHandler, HTTPServer
import json

class Handler(BaseHTTPRequestHandler):
    def _send(self, code, data):
        self.send_response(code)
        self.send_header("Content-Type", "application/json")
        self.end_headers()
        self.wfile.write(json.dumps(data).encode())

    def do_POST(self):
        body = self.rfile.read(int(self.headers["Content-Length"])).decode()
        self._send(201, {"id": 101, "received": body})

    def do_GET(self):
        self._send(200, [])

HTTPServer(("0.0.0.0", 8081), Handler).serve_forever()
```

```bash
python3 test_api.py &     # запуск сервера у фоні (всередині контейнера)

curl -i -X POST -d "title=foo&body=bar&userId=1" http://127.0.0.1:8081/posts
curl -i http://127.0.0.1:8081/posts
```

### Результат

```text
--- POST
HTTP/1.0 201 Created
Server: BaseHTTP/0.6 Python/3.12.3
Date: Sat, 10 Oct 2026 13:04:34 GMT
Content-Type: application/json

{"id": 101, "received": "title=foo&body=bar&userId=1"}
--- GET
HTTP/1.0 200 OK
Server: BaseHTTP/0.6 Python/3.12.3
Date: Sat, 10 Oct 2026 13:04:34 GMT
Content-Type: application/json

[]
```

`HTTP/1.0` у відповіді — особливість простого сервера `http.server`, на суть завдання це не впливає.

### Аналіз

| Запит | Статус | Що означає |
| --- | --- | --- |
| `POST /posts` | `201 Created` | Сервер прийняв дані й **створив новий ресурс**. У тілі повернув його `id` (101) і отримані дані. |
| `GET /posts` | `200 OK` | Запит успішний, сервер повернув список (тут порожній `[]`, бо тестовий сервер нічого не зберігає). |

### Різниця між POST і GET

| | GET | POST |
| --- | --- | --- |
| Де передаються дані | У URL (query string: `/posts?userId=1`) | У тілі запиту (body) |
| Мета | Отримати дані | Надіслати дані, створити ресурс |
| Змінює стан сервера | Ні (безпечний метод) | Так |
| Ідемпотентність | Так: повтор запиту дає той самий результат | Ні: кожен повтор може створити ще один запис |
| Кешування | Браузери й проксі можуть кешувати | Зазвичай не кешується |
| Видимість даних | Параметри видно в адресному рядку, історії браузера, логах серверів | Дані не видно в URL (але без HTTPS вони все одно не зашифровані) |

Тому паролі, форми та великі обсяги даних передають через POST, а GET використовують для читання.

## Завдання 3. Аналіз TLS-сертифіката (3 бали)

### Команди

```bash
openssl s_client -connect wikipedia.org:443 -servername wikipedia.org
```

`-servername` передає ім'я сайту в розширенні **SNI** (Server Name Indication). На одній IP-адресі може бути багато сайтів, і за SNI сервер обирає, який сертифікат показати.

### Результат (скорочено)

```text
subject=CN = *.wikipedia.org
issuer=C = US, O = Let's Encrypt, CN = YE2
New, TLSv1.3, Cipher is TLS_AES_128_GCM_SHA256
Verify return code: 0 (ok)
```

Версію TLS видно в рядку `New, TLSv1.3, ...`: саме там openssl показує узгоджений протокол і шифр.

### Аналіз

| Поле | Значення | Пояснення |
| --- | --- | --- |
| **Subject** | `CN = *.wikipedia.org` | Кому виданий сертифікат. `*` означає **wildcard-сертифікат**: він дійсний для будь-якого піддомену (`en.wikipedia.org`, `uk.wikipedia.org` тощо). |
| **Issuer** | `C = US, O = Let's Encrypt, CN = YE2` | Хто видав сертифікат: центр сертифікації (CA) **Let's Encrypt**, проміжний сертифікат `YE2`. Країна — США. |
| **Версія TLS** | `TLSv1.3` | Найновіша версія протоколу. Швидше рукостискання (1 RTT) і лише сучасні надійні шифри. |
| **Шифр** | `TLS_AES_128_GCM_SHA256` | Набір алгоритмів для захисту даних (див. нижче). |
| **Verify return code** | `0 (ok)` | Ланцюжок сертифікатів перевірено успішно: він веде до кореневого CA, якому довіряє система. Сертифікат дійсний. |

### Розбір шифрового набору `TLS_AES_128_GCM_SHA256`

| Частина | Що означає |
| --- | --- |
| `TLS` | Протокол. |
| `AES_128` | Симетричне шифрування даних алгоритмом AES з ключем 128 біт. |
| `GCM` | Режим роботи AES (Galois/Counter Mode). Це **AEAD**: одночасно шифрує дані і перевіряє їхню цілісність (дані не підмінили). |
| `SHA256` | Хеш-функція для HKDF — механізму виведення ключів сесії. |

У TLS 1.3 обмін ключами (ECDHE) і алгоритм підпису сертифіката узгоджуються окремо. Тому їх немає в назві набору, на відміну від TLS 1.2 (наприклад, `ECDHE-RSA-AES128-GCM-SHA256`).

## Завдання 4. Аналіз cookies (3 бали)

### Команди

```bash
curl -sI https://github.com | grep -i set-cookie
```

### Результат

```text
set-cookie: _gh_sess=E%2FeWNIiAfc...; path=/; HttpOnly; secure; SameSite=Lax
set-cookie: _octo=GH1.1.209674...; expires=Sun, 10 Oct 2027 13:04:35 GMT; domain=.github.com; path=/; secure; SameSite=Lax
set-cookie: logged_in=no; expires=Sun, 10 Oct 2027 13:04:35 GMT; domain=.github.com; path=/; HttpOnly; secure; SameSite=Lax
```

> Значення cookies `_gh_sess` і `_octo` я обрізала (`...`) з міркувань приватності, бо репозиторій публічний.

### Аналіз

| Cookie | Атрибути | Призначення |
| --- | --- | --- |
| `_gh_sess` | `path=/`, `HttpOnly`, `secure`, `SameSite=Lax`, без `expires` | Сесійна cookie GitHub. Немає `expires`, тому браузер видаляє її після закриття. |
| `_octo` | `expires` 2027, `domain=.github.com`, `secure`, `SameSite=Lax`, **без** `HttpOnly` | Ідентифікатор відвідувача для аналітики. Живе рік, діє на всіх піддоменах. Не `HttpOnly`, бо її читає JavaScript на сторінці. |
| `logged_in` | `expires` 2027, `domain=.github.com`, `HttpOnly`, `secure`, `SameSite=Lax` | Прапорець «чи увійшов користувач». Зараз `no`, бо запит був без авторизації. |

### Пояснення атрибутів

- **HttpOnly** — cookie недоступна для JavaScript (`document.cookie` її не бачить). Якщо на сайті є XSS-вразливість, шкідливий скрипт не зможе викрасти сесійну cookie.
- **Secure** — браузер надсилає cookie лише через HTTPS. Через незахищений HTTP її не відправить, тому її не перехоплять у відкритій мережі (атака MITM).
- **SameSite=Lax** — cookie не надсилається в міжсайтових підзапитах (картинки, iframe, `fetch`) і в міжсайтових POST-запитах. Надсилається лише при звичайному переході за посиланням. Це захист від **CSRF**: чужий сайт не зможе зробити дію від імені користувача.

## Завдання 5. Вибір протоколу для онлайн-біржі (4 бали)

**Ситуація:** онлайн-біржа, ціни змінюються щосекунди. Внутрішні сервіси білінгу та бухгалтерії потребують мінімальної затримки.

### A. Графік цін у браузері в реальному часі → **WebSocket**

- Одне постійне з'єднання між браузером і сервером замість нових запитів.
- **Full-duplex**: дані йдуть в обидва боки одночасно.
- **Server push**: сервер сам надсилає нову ціну, щойно вона змінилась. Клієнту не треба питати.
- Мінімальні накладні витрати: кадр WebSocket має кілька байтів заголовка, а не сотні байтів HTTP-заголовків на кожне оновлення.
- Двосторонність корисна і для біржі: клієнт може в тому ж каналі підписуватися на інші інструменти або надсилати заявки.

**Чому не polling?** Опитування сервера кожну секунду створює купу HTTP-запитів, більшість з яких марні. Це навантажує сервер, а ціна все одно приходить із запізненням до одного інтервалу опитування.

**Альтернатива — SSE** (Server-Sent Events). Простіший варіант поверх звичайного HTTP, але лише в один бік (сервер → клієнт). Підійде, якщо графік тільки показує ціни, а заявки надсилаються окремо.

### B. Обмін між мікросервісами білінгу та бухгалтерії → **gRPC**

- Працює поверх **HTTP/2**: мультиплексування багатьох викликів в одному з'єднанні, стиснення заголовків.
- Дані в бінарному форматі **Protobuf**: менші за JSON і швидше серіалізуються/десеріалізуються.
- **Строгий контракт** у `.proto`-файлі: типи полів перевіряються, код клієнта і сервера генерується автоматично. Для фінансових даних це зменшує помилки.
- Підтримує **стрімінг** (односторонній і двосторонній), наприклад, потік транзакцій.
- Результат — мінімальна затримка між сервісами.

**Чому не REST/JSON?** JSON текстовий і більший за обсягом, його довше розбирати. Немає строгої схеми. HTTP/1.1 обробляє запити в одному з'єднанні по черзі. Для внутрішнього високонавантаженого обміну це повільніше. REST краще залишити для публічного API.

### Порівняння

| Протокол | Напрям | Формат | Затримка | Де використовувати |
| --- | --- | --- | --- | --- |
| HTTP polling (REST) | клієнт → сервер, запит-відповідь | текст (JSON) | висока | рідкісні оновлення, публічні API |
| SSE | сервер → клієнт | текст | низька | стрічки новин, сповіщення, односторонні оновлення |
| WebSocket | двосторонній (full-duplex) | текст або бінарний | дуже низька | біржові графіки, чати, онлайн-ігри |
| gRPC | двосторонній, зі стрімінгом | бінарний (Protobuf) | дуже низька | обмін між внутрішніми мікросервісами |

**Висновок:** для браузера — WebSocket, для внутрішніх сервісів — gRPC.
