## Завдання 1. Відкриті порти (аналог `ss -tuln`)

```bash
netstat -an -p tcp | grep LISTEN   # TCP-сокети в стані LISTEN
netstat -an -p udp                 # UDP-сокети
```

### Аналіз

У macOS адреса і порт розділені крапкою: `*.5000` означає «будь-яка адреса, порт 5000». У Linux `ss` пише це як `0.0.0.0:5000` або `*:5000`.

**Відкриті TCP-порти (стан LISTEN):**

| Протокол | Порт | Адреса | Стан | Що це |
| --- | --- | --- | --- | --- |
| TCP | 5000 | `*` (усі інтерфейси, IPv4 + IPv6) | LISTEN | AirPlay Receiver (процес ControlCenter) |
| TCP | 7000 | `*` (усі інтерфейси, IPv4 + IPv6) | LISTEN | AirPlay Receiver (процес ControlCenter) |
| TCP | 50171 | `*` (усі інтерфейси, IPv4 + IPv6) | LISTEN | `rapportd` — зв'язок між пристроями Apple (Handoff, Continuity) |
| TCP | 57621 | `*` | LISTEN | Spotify — пошук пристроїв у локальній мережі |
| TCP | 2968 | `*` | LISTEN | EEventManager (Epson Event Manager) |
| TCP | 7768 | `127.0.0.1` | LISTEN | Spotify, локальний сервіс |
| TCP | 44950, 44960 | `127.0.0.1` | LISTEN | локальний агент Figma |

Приклад запису: **TCP порт: 5000 → AirPlay Receiver (ControlCenter)**.

**Різниця між `*` та `127.0.0.1`:**

- `*` — сервіс слухає на всіх інтерфейсах. До нього можна підключитися з інших пристроїв у мережі (наприклад, з iPhone на AirPlay).
- `127.0.0.1` — сервіс слухає лише на loopback. Підключитися можна тільки з цього ж комп'ютера. Так зроблено для Spotify (7768) і Figma (44950, 44960), бо ці порти потрібні лише локальним програмам.

**UDP-сокети:**

- Більшість рядків — це не сервери, а вихідні потоки: локальна адреса `192.168.88.22` з випадковим портом → віддалений сервер на порт **UDP 443**. Це протокол **QUIC** (HTTP/3), який працює поверх UDP. Адреси `142.250.x.x` / `142.251.x.x` належать Google, `18.244.x.x` — AWS, `35.186.224.x` — Spotify (Google Cloud).
- `*.57621` — справжній UDP-сокет, що чекає на дані (Spotify, пошук пристроїв у мережі).

**Чому в UDP немає стану LISTEN.** UDP не встановлює з'єднань, тому в нього немає станів LISTEN, ESTABLISHED тощо. Сокет просто відкритий і приймає датаграми. macOS залишає колонку стану порожньою, а Linux у `ss` показує такі сокети як **UNCONN** (unconnected).

Відкритих портів системи вистачило для завдання, тому окремий тестовий сервер (`python3 -m http.server 8080`) я не використовувала.

## Завдання 2. Процеси та PID (аналог `ss -tulpn`)

### Команди

```bash
sudo lsof -nP -iTCP -sTCP:LISTEN   # TCP-порти в стані LISTEN з процесами
sudo lsof -nP -iUDP                # UDP-сокети з процесами
```

```text
ControlCe   931 silence   10u  IPv6  ...  TCP *:7000 (LISTEN)
ControlCe   931 silence   11u  IPv4  ...  TCP *:5000 (LISTEN)
ControlCe   931 silence   12u  IPv6  ...  TCP *:5000 (LISTEN)
EEventMan   984 silence    4u  IPv4  ...  TCP *:2968 (LISTEN)

```

```text

launchd       1           root   30u  IPv4  ...  UDP *:138
launchd       1           root   31u  IPv4  ...  UDP *:137
```

### Аналіз

| Процес | PID | Протокол | Порт | Призначення |
| --- | --- | --- | --- | --- |
| `rapportd` | 880 | TCP | 50171 | зв'язок між пристроями Apple (Handoff, Continuity) |
| `ControlCenter` (`ControlCe`) | 931 | TCP | 5000, 7000 | AirPlay Receiver |
| `Spotify` | 1152 | TCP | 51663, 57621, 7768 (лише 127.0.0.1) | Spotify Connect, пошук пристроїв, локальний сервіс |
| `launchd` | 1 | UDP | 137, 138 | NetBIOS (імена та датаграми, мережа Windows/SMB) |

**Колонки `lsof`:**

- `COMMAND` — назва процесу (обрізана до 9 символів, тому `ControlCe`);
- `PID` — ідентифікатор процесу;
- `USER` — власник процесу;
- `FD` — номер дескриптора файлу (сокет у Unix — теж файл);
- `TYPE` — `IPv4` або `IPv6`;
- `NAME` — протокол, адреса:порт і стан.

Один процес може мати кілька сокетів: ControlCenter слухає два порти, і кожен окремо для IPv4 та IPv6.

**Чому потрібен `sudo`.** Без прав адміністратора `lsof` показує лише процеси поточного користувача. Системні процеси працюють від `root` (наприклад, `launchd` з PID 1). Їх видно тільки з `sudo`. У Linux так само: `ss -p` без `sudo` не показує процеси інших користувачів.

## Завдання 3. Перевірка TCP-з'єднання

### Команда

```bash
nc -vz google.com 80
```

### Результат

```text
Connection to google.com port 80 [tcp/http] succeeded!
```

### Аналіз

| Параметр | Значення |
| --- | --- |
| Протокол | **TCP** (`[tcp/http]`) |
| Порт | **80** (HTTP) |
| Результат | з'єднання **встановлено** (`succeeded!`) |

- `-v` — докладний вивід;
- `-z` — лише перевірити порт, не надсилаючи даних.

`succeeded` означає, що пройшло трикрокове рукостискання TCP: мій комп'ютер надіслав **SYN**, сервер Google відповів **SYN-ACK**, мій комп'ютер підтвердив **ACK**. Отже, порт 80 на сервері відкритий і приймає з'єднання. Через ключ `-z` `nc` одразу закрив з'єднання, не відправивши HTTP-запиту.

## Завдання 4. Порівняння UDP та TCP

### Команди

```bash
nc -u -vz 8.8.8.8 53   # UDP
nc -vz 8.8.8.8 53      # TCP
```

### Результат

UDP:

```text
Connection to 8.8.8.8 port 53 [udp/domain] succeeded!
```

TCP:

```text
Connection to 8.8.8.8 port 53 [tcp/domain] succeeded!
```

### Аналіз

Обидві команди перевіряють порт **53** (DNS) на публічному DNS-сервері Google `8.8.8.8`, але різними протоколами.

**TCP.** `succeeded` означає справжнє з'єднання. Відбулося рукостискання SYN → SYN-ACK → ACK, тобто сервер точно отримав запит і відповів. Порт 53/TCP відкритий.

**UDP.** Для UDP `nc` теж може написати `succeeded`, але це означає менше. UDP не встановлює з'єднання і не має рукостискання. `nc` лише надсилає датаграму. Якщо локально не виникло помилки, `nc` вважає перевірку успішною. Підтвердження від сервера немає: сервер може взагалі не відповісти (порожній пакет — це не коректний DNS-запит). Тому «успіх» для UDP показує лише те, що пакет пішов, а не те, що його отримали.

| Характеристика | TCP | UDP |
| --- | --- | --- |
| З'єднання | встановлюється (3-way handshake) | немає, датаграми надсилаються одразу |
| Гарантія доставки | так (підтвердження ACK, повторна передача) | ні |
| Порядок пакетів | зберігається (номери послідовності) | не гарантується |
| Швидкість | нижча, більше службових даних | вища, мінімальний заголовок (8 байт) |
| Що означає `succeeded` у `nc` | сервер прийняв з'єднання | датаграму надіслано без локальної помилки |
| Приклади | HTTP/HTTPS, SSH, пошта | DNS, QUIC (HTTP/3), відео- та голосові дзвінки, ігри |

**DNS використовує обидва протоколи.** Звичайні запити йдуть через **UDP 53**: вони короткі, і швидкість важливіша. **TCP 53** використовується, коли відповідь завелика для однієї UDP-датаграми, і для передачі зони між DNS-серверами (zone transfer). Тому `8.8.8.8` слухає порт 53 і по UDP, і по TCP.

## Завдання 5. DNS-запити

### Команди

```bash
nslookup wikipedia.org
dig wikipedia.org
```

### Результат

```text
Server:		192.168.88.1
Address:	192.168.88.1#53

Non-authoritative answer:
Name:	wikipedia.org
Address: 185.15.59.224
```

```text
;; ->>HEADER<<- opcode: QUERY, status: NOERROR, id: 2051
;; flags: qr rd ra; QUERY: 1, ANSWER: 1, AUTHORITY: 0, ADDITIONAL: 0

;; QUESTION SECTION:
;wikipedia.org.			IN	A

;; ANSWER SECTION:
wikipedia.org.		21	IN	A	185.15.59.224

;; Query time: 4 msec
;; SERVER: 192.168.88.1#53(192.168.88.1)
```

### Аналіз

| Параметр | Значення | Пояснення |
| --- | --- | --- |
| Домен | `wikipedia.org` | |
| IP-адреса | `185.15.59.224` | IPv4-адреса сервера Вікіпедії |
| Тип запису | `A` | запис, що зіставляє домен з IPv4-адресою |
| DNS-сервер | `192.168.88.1#53` | домашній роутер, порт 53 |
| TTL | 21 секунда | скільки ще часу запис можна зберігати в кеші |
| Час запиту | 4 мс | відповідь прийшла з кешу роутера, тому так швидко |
| Статус | `NOERROR` | запит виконано без помилок |

**DNS-сервер.** Запит обробив домашній роутер `192.168.88.1`. Цю адресу видав DHCP (див. ДЗ1). Роутер сам не знає адрес усіх доменів: він працює як **DNS-forwarder і кеш**. Він пересилає запит DNS-серверу провайдера або публічному резолверу і зберігає відповідь у кеші.

**Non-authoritative answer.** Відповідь отримано не від авторитетного DNS-сервера Вікіпедії (того, що зберігає зону `wikipedia.org`), а від проміжного рекурсивного резолвера з його кешу. Дані правильні, але це копія. У `dig` це також видно: прапорець `aa` (authoritative answer) відсутній, є лише `qr rd ra`:

- `qr` — це відповідь;
- `rd` — клієнт попросив рекурсивний пошук;
- `ra` — сервер підтримує рекурсію.

**TTL = 21 с.** Невелике значення, бо запис уже якийсь час лежить у кеші, і TTL зменшується. Через 21 секунду роутер видалить запис і запитає його знову.
