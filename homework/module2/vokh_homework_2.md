## Завдання 1. Відкриті порти (`ss -tuln`)

### Команди

У щойно створеному контейнері не працює жодного сервісу, тому, як підказано в завданні, я запустила тестові сервери:

```bash
python3 -m http.server 8080 &   # простий HTTP-сервер
# + невеликий тестовий API на Python на порту 8081 (використовується в ДЗ3)
ss -tuln
```

### Результат

```text
Netid State  Recv-Q Send-Q Local Address:Port Peer Address:PortProcess
tcp   LISTEN 0      5            0.0.0.0:8080      0.0.0.0:*
tcp   LISTEN 0      5            0.0.0.0:8081      0.0.0.0:*
```

### Аналіз

Ключі: `-t` — TCP, `-u` — UDP, `-l` — лише сокети, що слухають, `-n` — показувати номери портів, а не назви служб.

**Колонки:**

- `Netid` — протокол (`tcp` або `udp`);
- `State` — стан сокета (`LISTEN` — чекає на вхідні з'єднання);
- `Recv-Q` — для LISTEN: кількість з'єднань, що чекають на `accept()` (тут 0);
- `Send-Q` — для LISTEN: максимальна довжина черги (backlog). У Python `http.server` це **5**;
- `Local Address:Port` — адреса і порт, на яких слухає сервіс. `0.0.0.0` означає всі IPv4-інтерфейси;
- `Peer Address:Port` — віддалена сторона. Для LISTEN це `0.0.0.0:*`, бо з'єднання ще немає.

**Відкриті порти:**

| Протокол | Порт | Адреса | Стан | Що це |
| --- | --- | --- | --- | --- |
| TCP | 8080 | `0.0.0.0` (усі інтерфейси) | LISTEN | `python3 -m http.server` |
| TCP | 8081 | `0.0.0.0` (усі інтерфейси) | LISTEN | тестовий API на Python |

Приклад запису: **TCP порт: 8080 → HTTP-сервер Python**.

**Чому лише два порти.** Завдання просить щонайменше 3 порти, але в чистому контейнері відкриті тільки ті сервіси, які я запустила сама. Інших портів немає, і я не стала їх вигадувати. Для порівняння: на звичайному Linux-комп'ютері зазвичай також видно, наприклад, TCP 22 (SSH), TCP 631 (CUPS, друк) і UDP 68 (DHCP-клієнт). Це типові приклади, а не мій вивід.

**Чому немає UDP-сокетів.** У контейнері не працює жодної UDP-служби, тому `ss -u` нічого не показав. Якби UDP-сокет був, його стан був би **UNCONN** (unconnected), а не LISTEN. UDP не встановлює з'єднань, тому в нього немає станів LISTEN чи ESTABLISHED. Сокет просто відкритий і приймає датаграми.

## Завдання 2. Процеси та PID (`ss -tulpn`)

### Команда

```bash
ss -tulpn
```

### Результат

```text
Netid State  Recv-Q Send-Q Local Address:Port Peer Address:PortProcess
tcp   LISTEN 0      5            0.0.0.0:8080      0.0.0.0:*    users:(("python3",pid=3127,fd=3))
tcp   LISTEN 0      5            0.0.0.0:8081      0.0.0.0:*    users:(("python3",pid=3128,fd=3))
```

### Аналіз

| Процес | PID | Протокол | Порт | Призначення |
| --- | --- | --- | --- | --- |
| `python3` | 3127 | TCP | 8080 | `http.server` — тестовий HTTP-сервер |
| `python3` | 3128 | TCP | 8081 | тестовий API |

Ключ `-p` додає колонку `Process` у форматі `users:(("назва",pid=PID,fd=N))`:

- `"python3"` — назва процесу;
- `pid` — ідентифікатор процесу;
- `fd` — номер дескриптора файлу (сокет у Unix — теж файл). `fd=3`, бо 0, 1 і 2 зайняті stdin, stdout і stderr.

Обидва сервери — це процес `python3`, але різні екземпляри з різними PID. Саме за PID їх можна розрізнити (і, наприклад, зупинити командою `kill 3127`).

**Про `sudo`.** У контейнері команди виконувались від `root`, тому `sudo` не знадобився. На звичайній системі без `sudo` колонка `Process` порожня для процесів інших користувачів (наприклад, системних служб від `root`).

## Завдання 3. Перевірка TCP-з'єднання

### Команда

```bash
nc -vz google.com 80
```

### Результат

```text
Connection to google.com (142.250.130.101) 80 port [tcp/http] succeeded!
```

### Аналіз

| Параметр | Значення |
| --- | --- |
| Протокол | **TCP** (`[tcp/http]`) |
| Порт | **80** (HTTP) |
| IP-адреса | `142.250.130.101` (одна з адрес Google) |
| Результат | з'єднання **встановлено** (`succeeded!`) |

- `-v` — докладний вивід;
- `-z` — лише перевірити порт, не надсилаючи даних.

`succeeded` означає, що пройшло трикрокове рукостискання TCP: контейнер надіслав **SYN**, сервер Google відповів **SYN-ACK**, контейнер підтвердив **ACK**. Отже, порт 80 на сервері відкритий і приймає з'єднання. Через ключ `-z` `nc` одразу закрив з'єднання, не відправивши HTTP-запиту.

## Завдання 4. Порівняння UDP та TCP

### Команди

```bash
nc -u -vz 8.8.8.8 53   # UDP
nc -vz 8.8.8.8 53      # TCP
```

### Результат

UDP:

```text
Connection to 8.8.8.8 53 port [udp/domain] succeeded!
```

TCP:

```text
Connection to 8.8.8.8 53 port [tcp/domain] succeeded!
```

### Аналіз

Обидві команди перевіряють порт **53** (DNS) на публічному DNS-сервері Google `8.8.8.8`, але різними протоколами.

**TCP.** `succeeded` означає справжнє з'єднання. Відбулося рукостискання SYN → SYN-ACK → ACK, тобто сервер точно отримав запит і відповів. Порт 53/TCP відкритий.

**UDP.** Для UDP `nc` теж пише `succeeded`, але це означає менше. UDP не встановлює з'єднання і не має рукостискання. `nc` лише надсилає датаграму. Якщо локально не виникло помилки, `nc` вважає перевірку успішною. Підтвердження від сервера немає: сервер може взагалі не відповісти (порожній пакет — це не коректний DNS-запит). Тому «успіх» для UDP показує лише те, що пакет пішов, а не те, що його отримали.

| Характеристика | TCP | UDP |
| --- | --- | --- |
| З'єднання | встановлюється (3-way handshake) | немає, датаграми надсилаються одразу |
| Гарантія доставки | так (підтвердження ACK, повторна передача) | ні |
| Порядок пакетів | зберігається (номери послідовності) | не гарантується |
| Швидкість | нижча, більше службових даних | вища, мінімальний заголовок (8 байт) |
| Що означає `succeeded` у `nc` | сервер прийняв з'єднання | датаграму надіслано без локальної помилки |
| Приклади | HTTP/HTTPS, SSH, пошта | DNS, QUIC (HTTP/3), відео- та голосові дзвінки, ігри |

**DNS використовує обидва протоколи.** Звичайні запити йдуть через **UDP 53**: вони короткі, і швидкість важливіша. **TCP 53** використовується, коли відповідь завелика для однієї UDP-датаграми, і для передачі зони між DNS-серверами (zone transfer). Тому `8.8.8.8` слухає порт 53 і по UDP, і по TCP.

## Завдання 5. DNS-запити

### Команди

```bash
nslookup wikipedia.org
dig wikipedia.org
```

### Результат

```text
Server:		192.168.65.7
Address:	192.168.65.7#53

Non-authoritative answer:
Name:	wikipedia.org
Address: 185.15.59.224
Name:	wikipedia.org
Address: 2a02:ec80:300:ed1a::1
```

```text
;; ->>HEADER<<- opcode: QUERY, status: NOERROR, id: 46861
;; flags: qr rd ra; QUERY: 1, ANSWER: 1, AUTHORITY: 0, ADDITIONAL: 0

;; QUESTION SECTION:
;wikipedia.org.			IN	A

;; ANSWER SECTION:
wikipedia.org.		42	IN	A	185.15.59.224

;; Query time: 4 msec
;; SERVER: 192.168.65.7#53(192.168.65.7) (UDP)
```

### Аналіз

| Параметр | Значення | Пояснення |
| --- | --- | --- |
| Домен | `wikipedia.org` | |
| IPv4-адреса | `185.15.59.224` | запис типу `A` |
| IPv6-адреса | `2a02:ec80:300:ed1a::1` | запис типу `AAAA` (показав `nslookup`) |
| DNS-сервер | `192.168.65.7#53` | внутрішній DNS Docker Desktop, порт 53 |
| Транспорт | UDP | видно в рядку `SERVER: ... (UDP)` |
| TTL | 42 секунди | скільки ще часу запис можна зберігати в кеші |
| Час запиту | 4 мс | відповідь прийшла з кешу, тому так швидко |
| Статус | `NOERROR` | запит виконано без помилок |

**Типи записів.** `A` зіставляє домен з IPv4-адресою, `AAAA` — з IPv6-адресою. `nslookup` за замовчуванням запитує обидва типи, тому показав дві адреси. `dig` без параметрів запитує лише `A`.

**DNS-сервер.** Запит обробив `192.168.65.7` — це вбудований DNS-резолвер Docker Desktop, а не домашній роутер. Він сам не знає адрес усіх доменів: він пересилає запит DNS-серверу Mac, тобто домашньому роутеру, а той далі — DNS-серверу провайдера або публічному резолверу. Відповіді по дорозі кешуються.

**Non-authoritative answer.** Відповідь отримано не від авторитетного DNS-сервера Вікіпедії (того, що зберігає зону `wikipedia.org`), а від проміжного рекурсивного резолвера з його кешу. Дані правильні, але це копія. У `dig` це також видно: прапорець `aa` (authoritative answer) відсутній, є лише `qr rd ra`:

- `qr` — це відповідь;
- `rd` — клієнт попросив рекурсивний пошук;
- `ra` — сервер підтримує рекурсію.

**TTL = 42 с.** Невелике значення, бо запис уже якийсь час лежить у кеші, і TTL зменшується. Через 42 секунди резолвер видалить запис і запитає його знову.
